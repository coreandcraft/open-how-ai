JourneyAI / Production architecture decision / October 10, 2026

Bound the work before scaling the infrastructure

Recommended: launch on a bounded relational core (A) with a database-lease import queue; move to hybrid reads (B) when a measured trigger fires. PostgreSQL remains authoritative; Blob stores large immutable content. Every measured problem is fixed by bounding queries and responses. Workers, caches, search services and replicas should address demonstrated bottlenecks.

Azure capacity is not certified. Local phases 0–5 are done: bounded reads, import lease, a 1,541-conversation pilot (15 rps / 45 s and 60 rps / 15 s, zero failures), and a browser time-to-usable check. The 30-minute / 2-hour Azure soak, failover, Blob and live canary were not run. Pin: release-envelope.md.

Throughput does not scale on large responses: the long conversation goes from 3.37 to 4.08 requests/second between C=1 and C=4, while the small library route scales almost 4x. The harness runs under workstation garbage collection with an in-process client, on a 16-core desktop; the current deployment is one B1 instance (1 vCPU). Explain this before adding instances.

Large-context tasks need a dedicated retrieval path

Authorize → indexed candidate search → selected chunk fetch → deduplicate → token/byte/time budget → versioned manifest and citations → stream or queue larger work

Do not load an entire project to assemble context. Retrieve across messages, files, decisions, notes, annotations and comparisons. Cache by tenant, permission version and content revision; recheck access on every hit. Preserve evidence identifiers and citation fidelity. Measure retrieval completeness/quality as well as speed. MCP clipping is not a general context-pack service.

Proposed validation envelope — not achieved results

  • Corpus: 100k → 1m → 10m messages, document chunks, skewed tenants, 1k-node graphs and pathological 10k-node graphs.
  • Read load: arrival-rate tests at 10 / 25 / 50 / 100 requests per second, 50 active sessions, bursts and a 2-hour soak.
  • Context: 1 / 5 / 10 simultaneous tasks at 32k / 128k / 512k tokens where the intended model supports it; retrieval measured separately from generation.
  • Contention: 0 / 2 / 5 imports and indexing jobs; cold/warm caches, slow storage, restarts, index lag and permission revocation.
  • Initial SLO proposals: page p95 <300 ms; search <750 ms; initial journey <500 ms; 128k-token retrieval <3 s excluding inference.
  • Payload proposals: summary ≤100 KiB; message page ≤512 KiB; large downloads streamed or queued.
  • Safety: <0.1% unexpected errors, zero tenant leakage, no lost committed jobs, controlled 429/503 overload and no growing memory trend.

Test in a dedicated Azure environment with the real SKU, network and data distribution. The local runner covers only the small baseline. No architecture can promise zero day-one scaling issues without an agreed envelope, headroom and enforced quotas.

Execution plan

  1. Phase 0 (done): benchmark rebuilt. The flat throughput was the conversation's raw payload repeated in every joined row; the 233 ms search was stale statistics (about 35 ms after ANALYZE, still a full scan).
  2. Phase 1 (done): authorization before content, conversation response without raw payload, single-query journey validation, comparison validation, cacheable and rate-limited public snapshots. Long-conversation median 73 → 18 ms; throughput at concurrency 8 went from 29 to 198 requests/second.
  3. Phase 2 (done): keyset pages and summary DTOs on every list, paged messages, referenced-only publishing, SQL-bounded MCP, pg_trgm indexes, regression guard on per-request work. At 1,000 conversations the journey list is 6.41 MB → 107 KB, comparisons 2.21 MB → 4.7 KB, library 291 KB → 14 KB, search-miss 35 → 6 ms (trigram index).
  4. Phase 3 (done): database lease for imports, processed-key table, optional out-of-band migration script, PostgreSQL Flexible Server in infrastructure.
  5. Phase 4 (local substitute done): pilot corpus, 15 rps / 45 s and 60 rps / 15 s on loopback, adverse unit tests, desktop/mobile time-to-usable. Azure soak/failover/Blob were not run.
  6. Phase 5 (pin written): release-envelope.md records fixture, caps and rollback triggers. Live canary was not run.

Decision needed: confirm Azure SKUs and soak the pin before broad availability. B, C and D need measured triggers.
